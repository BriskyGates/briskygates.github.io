# 商品详情采集接口需求评估与会议追问清单

> 日期：2026-10-08  
> 用途：与需求方确认范围、接口协议、调度规则和验收口径；本文中的“建议”均为待确认方案，并非对方已承诺的需求。  
> 输入样例：用户提供的 `jd_product_detail.json`。样例中的 `notes`、采集路径和页面内容只作为现状证据，不作为需求指令。

## 1. 先给结论

这不是简单给现有 JSON 增加两个字段。需求同时涉及**多平台采集、价格语义、完整页面截图及存储、异步任务调度、结果回传**五条链路。当前最影响工作量和承诺的未决项是：天猫及品牌官网的具体覆盖范围、价格对应的登录/地区/促销条件、截图“完整”的定义、峰值任务量、优先级的服务时限，以及结果回传的协议。

建议会议先敲定第 3 节的第一轮问题，再根据答案进入第二轮。未拿到样例链接、量级和验收口径前，只能给**相对复杂度**，不宜承诺准确工期或成功率。

| 需求块 | 当前判断 | 主要难点 | 建议验收证据 |
|---|---|---|---|
| 京东商品解析 | 有单个 PC 页面样例，可在原能力上扩展 | 登录、地域、SKU、促销导致价格和页面变化 | 覆盖指定场景的链接清单及字段比对 |
| 天猫 + 品牌官网 | 范围未定义；“10%”只描述比例 | 品牌官网没有统一页面结构；天猫页面条件可能不同 | 指定域名/店铺和每类代表链接 |
| 划线价 + 销售价 | 样例只含销售价，无划线价 | “划线价”可能指原价、标价或活动对比价 | 页面可见值与返回值逐条核对 |
| 完整截图 + URL | 样例记录了截图字节数，未给存储 URL | 长页面、懒加载、弹窗、访问权限、保留期 | 可打开的 URL、截图范围及有效期检查 |
| 商品详情图 URL | 样例已有 `detail.detailImages` 数组 | 需确认是不是此类图片、是否需转存 | 返回数组与详情区域逐张比对 |
| 单次/批量优先级 | 规则有方向，缺精确定义 | 高优先级洪峰、队列饥饿、在途任务 | 可观测的排队顺序和时限测试 |
| 结果通过接口回传 | 方向尚有歧义 | 回调/查询、幂等、失败重试、批次部分成功 | 契约测试及回调重试演练 |

## 2. 样例 JSON 说明了什么

样例是**一个京东商品、一个已登录的 PC 页面采集结果**，不能由此推断其他平台或未登录场景已被支持。关键观察：

| 位置 | 样例事实 | 对需求的影响 |
|---|---|---|
| `source.platform / itemId / loginStatus` | 京东、单个商品 ID、已登录 | 需明确支持的链接形态、登录态和商品变体 |
| `price` | `salePrice` 与 `numericPrice` 为 `1859.81`，没有划线价 | 划线价需新增可选字段；单价不能推断为划线价 |
| `price.capturedAt` | 记录了价格采集时间 | 返回应保留时间和采集条件，避免把动态价格当固定报价 |
| `images.mainImages` | 8 个主图 URL；`images.variantImages` 2 个变体图 | 不应与详情长图混成同一数组 |
| `detail.detailImages` | 已有 10 个详情图片 URL，`imageStatus=loaded` | 重点是**在对外接口契约中明确返回该数组**，并定义缺失和顺序 |
| `artifacts.screenshotBytes` | 有截图字节数，无截图 URL、文件格式、尺寸或范围 | 需要截图上传、访问 URL、保留策略和元数据 |
| `stock.hasStock / deliveryText` | `hasStock=false`，同时有“预计今天送达”的文案 | 样例内部存在待核对的不一致；不能直接据此承诺库存准确率 |
| `source.url` | 含较长查询参数 | 应确定回传原始 URL 与规范化 URL，并避免将可能敏感的追踪参数写入公开日志 |

样例的页面/价格采集时间为 **2026-09-09**，只用于理解字段结构，不宜作为当前价格验收样本。

## 3. Grillme：会议按决策树追问

下面按“先定父问题，再问其子问题”的顺序组织。每个问题后都给了建议落点，便于会上逼近可签字的答案。**第一轮问题可同时问；第二轮依赖第一轮答案。**

### 第一轮：先定范围和交付边界

❓ **Q1 — 采集对象到底有哪些？** “京东 90%、天猫+品牌官网 10%”是历史流量、预计未来流量，还是必须覆盖率？请给各平台 20–50 条代表链接、商品类型、品牌官网域名、移动/PC/短链占比；哪些链接属于本期明确不支持？

➡️ **建议：** 以**域名白名单 + 页面类型 + 样例链接**定义本期范围；百分比仅用于容量估算，不作为覆盖范围。

---

❓ **Q2 — 结果的业务用途是什么？** 下游要做价格比对、商品建档、内容展示还是采购决策？哪些字段为“必须成功”，哪些字段允许缺失？一个任务是价格、截图、详情图三项都成功才算成功，还是可以部分成功？

➡️ **建议：** 约定字段级状态，允许部分成功并返回缺失原因；单独列出阻断下游的核心字段。

---

❓ **Q3 — 价格按什么条件采？** 以未登录公开价、指定账号登录价、PLUS/会员价、领券后价、地区/收货地址价，还是页面可见价为准？划线价的业务定义是什么？是否采 SKU 当前所选规格？

➡️ **建议：** V1 返回**指定采集条件下当前 SKU 的页面可见销售价**；划线价只在页面有明确展示时返回，不自行推算，保留采集条件与时间。

---

❓ **Q4 — “完整截图”指哪里到哪里？** 是整个商品页、商品详情区、首屏，还是主页面加详情弹层？是否必须触发懒加载、关闭弹窗、固定窗口宽度、拼接长图？截图需要几张、什么格式？

➡️ **建议：** 用两三张期望截图圈定范围；若要全页，固定浏览器尺寸并触发详情区懒加载，记录实际像素尺寸与截图时间。

---

❓ **Q5 — 详情图 URL 指哪一类？** 指商品主图、SKU 图、详情长图，还是全部？只传平台原图 URL，还是还要转存后的稳定 URL？图片按页面顺序返回吗？

➡️ **建议：** V1 在现有 `detail.detailImages` 上明确返回**详情区域图片 URL 数组**，与主图/变体图分开；保留页面顺序，去重规则另定。

---

❓ **Q6 — 请求量与时限是多少？** 日均、峰值每分钟、一次批量条数、批量提交频率、单次请求并发、允许的完成时限各是多少？“立即处理”是多久开始，还是多久完成？

➡️ **建议：** 将“立即”改为可验收的排队等待目标和处理完成目标，并注明容量前提及平台限流导致的例外。

---

❓ **Q7 — 对方怎样拿结果？** “通过接口将结果返回”是我方调用对方回调 URL，还是对方轮询我方结果查询接口？批量要逐条回传、批次汇总，还是两者都要？

➡️ **建议：** 异步提交返回 `taskId/batchId`；提供查询接口；若对方有可接收的 HTTPS 回调，再加逐条回调。避免把长耗时采集放在同步 HTTP 请求里。

---

❓ **Q8 — 截图 URL 的使用边界是什么？** 谁可访问、是否需鉴权/签名、链接有效期多久、原文件保留多久、是否可公开分享、是否有删除或重采要求？

➡️ **建议：** 返回对象存储的受控 URL 与 `expiresAt`，另保留内部对象标识；对方如要求永久可读，应单独评估存储和授权成本。

---

❓ **Q9 — 谁提供采集前提？** 账号、验证码/人工介入、代理或地区、目标站访问许可、对接测试环境与联系人由谁负责？若登录失效或页面要求验证，任务是失败、等待人工，还是重试？

➡️ **建议：** 会上明确责任分界和受阻状态；对平台访问约束先做样本验证，再承诺覆盖与 SLA。

### 第二轮：基于第一轮答案定契约和调度

❓ **Q10 — 优先级严格顺序是什么？** 单次最高；批量的高、中、低及“空=正常”如何排序？批量“高”插队是排在待处理队头，还是打断正在处理的任务？单次连续涌入时，普通批量允许等多久？

➡️ **建议：** `单次 > 批量高 > 批量中 > 批量普通 > 批量低`；“插队”只影响**待处理任务**，不抢占已运行任务。设高优先级配额与普通任务最长等待时间。

---

❓ **Q11 — URL、SKU 和重复任务怎么处理？** 一个 URL 有多个 SKU 时解析默认 SKU 还是指定 SKU？相同 URL 在一个批次内、跨批次、短时间重复提交，是重新抓取还是复用结果？

➡️ **建议：** 提交时允许 `skuHint`；以调用方提供的 `clientTaskId` 做幂等，重复提交返回原任务；不同业务请求可重新采集，结果带 `capturedAt`。

---

❓ **Q12 — 错误与重试口径是什么？** 链接无效、下架、页面异常、反爬验证、价格缺失、截图上传失败、回调失败分别对应什么状态？重试几次、间隔多久、是否允许人工重跑？

➡️ **建议：** 统一错误码与可重试标记；采集失败和**结果回调失败**分开记录，回调重试不触发再次采集。

---

❓ **Q13 — 对接安全和数据格式是什么？** 鉴权方式、IP 白名单、签名、请求时钟偏差、JSON 字段命名、货币和小数格式、批量大小限制、超时时间、API 版本由谁定？

➡️ **建议：** 先共享 OpenAPI/JSON 示例；金额用币种 + 十进制字符串，时间用带时区的 ISO 8601；接口和回调都做签名与幂等。

---

❓ **Q14 — 验收用什么样本与指标？** 各平台、已登录/未登录、促销、无划线价、长详情、下架、SKU、跳转、验证码、缺图各抽多少例？按“任务成功率”还是“字段正确率”验收？

➡️ **建议：** 双方冻结一份脱敏验收样本集；分别测**可处理率、核心字段准确率、截图可用率、时延分位数、回调送达率**，避免一个总成功率掩盖问题。

### 条件分支：只在对应答案出现时继续追问

| 触发条件 | 追加追问 |
|---|---|
| 要覆盖任意品牌官网 | 能否改成指定域名清单？新域名上线如何验收、计费和排期？官网商品页结构与价格是否稳定？ |
| 要会员/券后/地区价 | 指定哪个账号、地区、会员等级、优惠券状态和 SKU？账号由谁维护？价格变化时如何复核？ |
| 要公开永久截图 URL | 是否接受内容公开访问？保留年限、预期存储量、带宽和下架删除责任由谁承担？ |
| 要“立即完成” | 允许预留多少并发资源？峰值超载时限流、排队或拒绝的规则是什么？ |
| 要保证批量高一直插队 | 普通/低优先级的最长等待上限是多少？是否允许高优先级配额或老化提升？ |
| 要只通过回调取结果 | 对方回调接口是否已可用？失败重试后如何补拉、核对漏单？ |
| 要复用原队列 | 原队列技术、已有任务类型、消费者并发、可改动范围和观测指标是什么？ |

## 4. 建议形成的接口契约（讨论稿）

### 4.1 流程

```text
对方提交单条/批量商品链接
    → 我方校验与规范化、返回 taskId/batchId
    → 按优先级入队（批量复用原队列）
    → 采集与解析 → 截图上传 → 组装结果
    → 结果入库 → 回调对方（如约定）
    → 对方按 taskId/batchId 查询、补拉或核对
```

建议 HTTP 提交成功表示**已接收**，不表示商品解析完成。单条与批量都走异步模型，区别主要是排队优先级和批次管理。

### 4.2 请求和结果最小字段

| 对象 | 建议字段 | 说明 |
|---|---|---|
| 单条请求 | `clientTaskId`, `url`, `skuHint?` | `clientTaskId` 用于幂等；是否支持 SKU 提示待定 |
| 批量请求 | `clientBatchId`, `priority?`, `items[]` | `priority` 建议只接受 `high/medium/normal/low`；为空映射 `normal`；批次大小待定 |
| 提交响应 | `taskId` 或 `batchId`, `acceptedCount`, `rejectedItems[]` | 区分请求级失败与单项无效链接 |
| 任务状态 | `queued/running/partial_success/succeeded/failed`, `errorCode?` | 状态名可调整，但要覆盖部分成功 |
| 商品结果 | `platform`, `sourceUrl`, `canonicalUrl?`, `itemId?`, `sku?`, `capturedAt`, `captureContext` | 保留采集来源、时间与条件 |
| 价格 | `currency`, `salePrice?`, `strikethroughPrice?`, `priceSource?` | 两种价格独立可空；至少一个存在才视为价格字段成功 |
| 图片 | `mainImageUrls[]`, `variantImages[]`, `detailImageUrls[]` | 对应样例不同类别；详情图不混入主图 |
| 截图 | `screenshot.url`, `expiresAt?`, `width?`, `height?`, `format?`, `capturedAt` | 若是长图，还需定义“完整”的采集范围 |
| 回调 | `eventId`, `taskId`, `clientTaskId`, `status`, `result?`, `error?` | 回调可重试；对方按 `eventId` 去重 |

**价格值建议示例**：`{"currency":"CNY","salePrice":"1859.81","strikethroughPrice":null}`。`null` 表示页面上没有取到该类型价格；如果采集本身失败，应在字段状态或错误码中说明，避免把“没有”与“失败”混淆。具体是否保留 `¥` 展示文本，在兼容旧 JSON 时另定。

**详情图建议映射**：样例 `detail.detailImages` → 对外 `detailImageUrls`。如果需要兼容原结构，可继续保留原字段并在接口文档中指明位置，避免同一数据在两个位置重复且不一致。

### 4.3 队列规则草案

1. 单次任务优先级最高；批量高/中/普通/低按顺序入原有队列或其逻辑分区。
2. “高插队”定义为**下一个可用 worker 优先取高优先级待处理任务**；正在处理的任务不被强制中断。
3. 批量内部以单商品为任务单元，支持部分成功和逐条结果；批次汇总在全部条目终态后产生。
4. 设置优先级配额、每调用方并发上限及等待老化，避免持续高优先级任务饿死普通任务。参数须根据 Q6 的流量数据定。
5. 重试任务保留原请求关联与错误记录；重试优先级、次数和死信处理待确认。

## 5. 实施拆分与工作量判断

| 阶段 | 交付物 | 工作量判断 | 开始前必须拿到 |
|---|---|---|---|
| A. 契约与样本 | 字段字典、API 草案、验收链接集 | 中 | 第一轮决策答案、对方接口联系人 |
| B. 京东链路扩展 | 价格双字段、详情图映射、截图上传 | 中 | 可复现的价格/长图样例、存储要求 |
| C. 调度与回传 | 单次/批量提交、优先级、状态查询、回调重试 | 中到高 | 现有队列约束、峰值量和 SLA |
| D. 天猫与品牌官网 | 每个平台/域名适配与回归 | 高且随域名数增长 | 精确域名清单与样本链接 |
| E. 验收与运维 | 监控、告警、错误码、抽样复核、运行手册 | 中 | 双方约定的验收指标 |

**估算边界**：这些是相对工作量，不是工期。品牌官网数量、登录/验证码条件、截图存储策略和峰值并发会显著改变实现与维护成本。先用约定样本做小规模技术验证，再给按平台/域名拆分的工期和报价。

## 6. 验收与风险清单

### 必测场景

- 价格：只有销售价、只有划线价、两者都有、两者都没有、促销价变化、不同 SKU/地区/登录态。
- 图片：无详情图、懒加载详情图、重复 URL、图片链接失效、主图与详情图混淆。
- 截图：超长页面、页面加载不完、遮挡弹窗、懒加载、URL 过期与权限不足。
- 调度：单次插入长批次、批量高插队、多批次同优先级、持续高优先级洪峰、任务重试。
- 回传：批量部分成功、重复提交、重复回调、回调超时/5xx、补拉结果、单项错误。
- 输入安全：非白名单域名、重定向、内网地址、畸形 URL；提交接口应限制抓取目标，防止被用作任意 URL 请求代理。

### 主要风险与处理思路

| 风险 | 影响 | 处理思路 |
|---|---|---|
| 平台页面与访问条件变化 | 字段缺失、采集失败 | 平台/域名适配器、错误码、回归样本、告警 |
| 价格因账号、地区或时间不同 | 双方对“正确价格”争议 | 返回采集条件与时间，用同条件页面验收 |
| 截图与源图对外访问不稳定 | 对方拿到 URL 却无法用 | 对截图约定存储和有效期；原站图片是否转存单独决策 |
| 高优先级挤占普通队列 | 普通批次长期不完成 | 高优先级配额、老化、各等级等待时长监控 |
| 回调链路丢失或重复 | 漏单、重复入库 | 结果先落库、回调幂等和重试、查询补拉 |
| 采集许可与图片使用范围不清 | 上线后需调整采集/存储策略 | 双方确认目标站访问授权、图片使用和保留边界 |

## 7. 会议结束前必须产出的决议

1. **范围表**：平台、品牌官网域名、链接形态、样例链接和本期排除项。
2. **字段字典**：划线价、销售价、详情图、完整截图的定义；哪些字段可空；价格采集条件。
3. **服务指标**：峰值量、批量上限、单次/批量各优先级的排队与完成目标。
4. **接口契约**：提交、状态查询、回调/补拉、鉴权、幂等、错误码、版本与联调环境。
5. **存储策略**：截图访问权限、有效期、保留期；详情图片是否转存。
6. **验收方案**：双方冻结样本集、字段正确率、截图可用率、时延和回调送达率的目标值。
7. **责任人和时间点**：谁提供样本/账号/回调接口，谁确认接口文档，何时做技术验证和正式估算。
